# 架构

## 一、分层

```
┌─────────────────────────────────────────────┐
│ 接入层                                       │
│   CLI（交互 / run --json）   RPC 宿主（JSONL）│
└───────────────┬─────────────────────────────┘
                │ AgentEvent（单向事件流）
┌───────────────▼─────────────────────────────┐
│ 循环层  AgentLoop                            │
│   内层：模型 → 工具 → 模型（含插话）          │
│   外层：追加任务（follow-up）                 │
│   旁挂：Compact（超预算折叠） Session（落盘） │
└───────┬───────────────────────┬─────────────┘
        │                       │
┌───────▼──────────┐   ┌────────▼─────────────┐
│ 模型层 Provider   │   │ 工具层 Tools          │
│ OpenAI 兼容 + SSE │   │ 内置 7 + 检索 + MCP       │
└──────────────────┘   └────────┬─────────────┘
                                │
                       ┌────────▼─────────────┐
                       │ 安全层 Sandbox       │
                       │ 策略：路径/环境/命令  │
                       │ 白名单：命令前缀       │
                       │ 执行：spawn + 超时    │
                       │ 握手：token 校验      │
                       └──────────────────────┘
┌─────────────────────────────────────────────┐
│ 循环层旁挂的闸门                              │
│   确认：写文件 / 执行 / 外部工具 前问人         │
│   重试：只在没产出任何东西时，最多 N 次         │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│ 提示词装配（启动时一次）                      │
│   固定安全边界 → 工作区 AGENTS.md → 额外要求   │
└─────────────────────────────────────────────┘
```

约束：**跨层只能单向调用**。工具层不许自己 `spawn`，接入层不许直接读文件，模型层不许知道工作区在哪。

## 二、双循环

### 2.1 内层（推进任务）

```
while 轮次 < maxTurns:
    把排队的插话并入上下文
    请求模型（流式）
    出错 / 被取消 → 结束本次运行，交由上层决定是否重试
    有工具调用：
        如果 finish_reason === "length"：参数可能被截断 → 不执行，回灌错误让模型重发
        否则逐个执行，把结果并入上下文
    没有工具调用：
        还有插话 → 继续循环
        没有插话 → 内层结束
```

### 2.2 外层（接续任务）

内层自然结束后，检查 follow-up 队列。有就作为新的 user 消息再来一轮，没有才算这次运行结束。

### 2.3 为什么插话和追加要分开

- 插话（steering）是**改变当前任务**：用户看到 Agent 跑偏了，说"别动那个文件"。它必须在**下一次请求模型之前**进入上下文。
- 追加（follow-up）是**任务完成后的下一步**："顺便把测试也跑了"。它不该打断当前任务。

混成一队，就会出现"用户中途纠正了一句，结果被排到整个任务结束才生效"。

## 三、状态机

唯一权威：`snapshot.isStreaming`。

```
idle ──submit──▶ chatting ──(无工具调用 & 无插话)──▶ idle
                    │                                ▲
                    └── error / aborted ─────────────┘
```

要点：

1. **不用事件判定结束**。`turn_end` 只代表一轮结束，之后可能还有追加任务；收到 `agent_end` 后仍可能发生重试或上下文压缩。
2. **`agent_settled` 的语义是"已确认空闲"**，发出时 `isStreaming` 必须已经是 `false`。测试里对这一点有断言。
3. **置位先于 await**。`submit()` 第一行就判断并置位，否则同一 tick 的第二次提交会读到旧状态，被当成新任务而不是插话。

## 四、模型层

- 只支持 OpenAI 兼容的 `/chat/completions`，流式。国产模型（DeepSeek / Qwen / GLM / Kimi / MiniMax）与聚合网关（OpenRouter、MixRoute、百炼、方舟）都能直接接。
- SSE **只按 `\n` 切**。行内可能夹带超长 JSON，用 `readline` 解析会让工具调用参数错位。
- 工具调用按 `index` 拼装，`id` 缺失时补一个稳定值，避免上游不规范导致消息不合法。
- 报错先脱敏再抛出，并标注 `retryable`（429/5xx 可重试，4xx 不可）。

### 4.0 模型解析（v0.5）

配置里的 `model` 可能是一个**别名**。`resolveModel` 把它解析成 `{ model, baseUrl, apiKey }`：别名可以只写模型名（线路与 key 回落到主配置），也可以带自己的 `baseUrl` / `apiKey`（走另一家网关）。别名里 `model` 为空视为没命中，回落到裸模型名——不能把空字符串发给上游，那样只会换来一个看不懂的 400。

同一套解析给压缩用：`compactModel` 指向的模型（通常是别名）负责生成上下文摘要。这是「按任务选模型」唯一的落地处，也是最不容易选错的一处——折叠是纯体力活，用主模型的额度做没有收益。

### 4.1 提示词装配（v0.4）

系统提示词在会话开始时**拼一次**，之后整条会话不变。拼装顺序是固定的三段：

```
固定段（人写死）      身份、工作区、工作方式、安全边界
       ↓
项目约定（AGENTS.md） 先写一段「不得放宽安全边界」的声明，再贴正文
       ↓
额外要求（--system-extra / FEIMA_SYSTEM_EXTRA）
```

顺序不是审美问题。**项目约定必须排在安全边界之后**：模型读到的顺序是「你的边界是什么 → 项目想让你做什么」。反过来，它会先接受项目要求，再看到限制，而限制里写的东西与已接受的要求冲突时，模型更可能迁就已接受的那条。

读取 `AGENTS.md` 的四条约束（都在 `loadProjectMemory` 里，改之前先看 ADR-012）：

1. 只读工作区**根目录**这一个文件，不向上遍历、不读子目录同名文件；
2. 符号链接按 `realpath` 判断，真实路径不在工作区内就当作不存在；
3. 上限 32 KB，按 Buffer 切再整体解码（按字符切会切断多字节字符），超出时在提示词里明说已截断；
4. 文件里含 `\0` 视为二进制，直接不读。

会话恢复（`feima resume`）时系统提示词**用当前配置重建**，不沿用旧会话里的那条——否则改了 `AGENTS.md` 之后老会话永远读不到新约定。

## 五、工具层

`Tool` 接口四件套：`name` / `description` / `parameters`（JSON Schema）/ `effects` + `run(args, ctx)`。

`effects` 是副作用标签（`read` / `write` / `exec` / `external`），不写视为只读。它被两处消费：

- **确认闸门**（`safety/confirm.ts`）：`--confirm` 的模式与标签一起决定「这次调用要不要问人」。
- **权限档**（`filterByPerms`）：`--perms read` 时把 `write_file` / `edit_file` / `bash` 从工具列表里**移除**，而不是留着再拒绝。

`selfConfirmed` 是唯一的例外标记：MCP 工具自己负责确认（因为只有它知道要说明「跑在策略层之外」），loop 不再重复问一遍。漏标只会多问一次，不会少问——默认方向是安全的。

- 参数一律手动校验并给出人话错误，不引 zod（零依赖原则）。
- 所有路径先进 `resolveRead` / `resolveWrite`，再碰 `fs`。
- 输出截断：读文件 1MB 上限、命令输出 256KB 上限、grep 300 条上限。上下文是稀缺资源，宁缺毋滥。
- 命令统一走 `ctx.exec`，工具层拿不到 `child_process`。

工具的三种来源，能力边界不同，装法也不同：

| 来源 | 例子 | 何时可用 | 约束 |
| --- | --- | --- | --- |
| 内置 | `read_file` / `bash` | 永远 | 走策略层与沙盒 |
| 知识库检索 | `search_knowledge` | 配了 `FEIMA_KB_URL` 才注册 | 结果截断、凭据只在内存 |
| MCP 外部 | `mcp__<server>__<tool>` | 显式 `--mcp` 打开 | 逐次确认或放行列表 |

**未配置就不注册**是这一层的统一规则：注册一个永远报错的工具，模型会反复试，几轮就把上下文烧完。缺什么由 `doctor` 报，不占模型注意力。

### 5.1 外部工具（MCP）

MCP 客户端只实现三个方法：`initialize` / `tools/list` / `tools/call`。规范里其余部分（resources、prompts、sampling、通知流）一个都没做——**协议支持度按需要走，不按规范走**，实现了也只是多一堆没人测的分支。

传输是 stdio + 换行分隔 JSON-RPC。解析层有个刻意的宽容：遇到非 JSON 行只记一笔噪音，不当致命错误。规范要求服务端 stdout 只写协议，但现实里有服务端会打启动横幅，一个 `console.log` 不该让整套工具不可用。

启动方式在 Windows 上单独处理（`buildSpawn`），因为「能跑 `npx`」和「参数不被拆开」在 `shell: true` 下不可兼得：

| 命令形态 | 怎么启动 |
| --- | --- |
| 绝对路径 / 含分隔符 | 直接 spawn，不过 shell |
| 裸名字 | 自己按 `PATH` + `PATHEXT` 查；查到 `.exe` / `.com` 直接 spawn |
| `.cmd` / `.bat` | 只能经 `cmd.exe`，参数逐个加引号 |

工具包装层（`mcp/tools.ts`）负责三件事：加前缀 `mcp__<server>__<tool>`（防撞名，撞名等于绕过策略层）、参数摘要脱敏后进确认弹窗、把 `isError` 与文本内容翻译成 `ToolResult`。

确认闸门的接线是这一层唯一容易出错的地方：`AgentLoop` 的 `confirm` 必须真的传进 `ToolContext`。传丢了不会报错——所有组件级用例都是绿的，表现只是「MCP 配了也调不动」，每次调用都被判成「无人确认」而拒绝。所以专门有一条端到端用例跑完整链路：假 provider 要 MCP 工具 → loop 问人 → 人同意 → 真实返回回灌给模型。

### 5.2 知识库检索工具

`search_knowledge` 调知识库的 `POST /api/ai/search`（chunk 检索，不经大模型，秒级返回），返回带编号的片段，最多 8 条、单条 400 字。

- **未配置就不注册**：注册一个永远报「未配置」的工具，模型会反复试，几轮烧完上下文。
- **凭据只在内存**：直接给 token，或用账号密码换一个（进程内缓存）。不落盘、不进日志、不传给子进程。
- **超时与取消都要生效**：`AbortSignal.any([ctx.signal, AbortSignal.timeout(t)])`。写成 `ctx.signal ?? timeout` 的话，一旦有 `ctx.signal` 就再也不会超时。

它只做检索，不做「外部记忆」替代摘要——压缩是长会话的基础设施，不能把它的可用性绑到一个网络服务上（ADR-013）。

## 六、安全层

### 6.1 五层机制

| 层 | 实现 | 防什么 |
| --- | --- | --- |
| 路径围栏 | `realpathLoose` + `isInside` | `../`、符号链接穿越（`workspace/link -> /etc`） |
| 读写黑名单 | denyRead 7 项 / denyWrite 6 项 | 凭据文件、`.env`、`.git/hooks` 持久化、`.agents`/`.codex` 横向移动 |
| 环境变量白名单 | 正则放行 16 类，强制 `TERM=dumb` | 子 shell 一句 `env` 打印出所有 API Key |
| 命令策略 | `guardCommand` 正则拦截 | `rm -rf /`、`mkfs`、强推、`curl \| sh`、fork 炸弹 |
| 命令白名单（可选） | `safety/allowlist.ts` 切段 + argv 前缀匹配 | 白名单外的任何命令（含 `;` `\|` 后的第二段） |
| 副作用确认（可选） | `safety/confirm.ts` + loop 执行前询问 | 未经同意的写文件 / 执行命令 / 外部工具调用 |
| 握手 + 失败即阻断 | 受控命令带回随机 token，20s 超时 | "扩展加载成功但没生效"的假绿 |

### 6.2 为什么 `.git/hooks` 要单独拦

git 进程在沙盒外。Agent 只要写一个 `pre-commit`，下次提交时就能执行任意代码，**完全绕过**所有隔离设计。这不是越权读写，是沙盒逃逸。

同理 `.agents` / `.codex`：用 A 的沙盒去改 B 的规则，是典型的横向移动。

### 6.3 隔离后端（v0.3）

`policy` 模式下进程本身没有沙箱，只有入口被策略过滤。`strict` 要的是另一件事：**即使命令绕过了所有正则，它也碰不到工作区之外的东西**。

实现靠三个后端，契约在 `src/safety/isolation.ts`：

```
availability() → 能不能用，不能用的原因（要具体到能动手修）
prepare()      → 建 profile、授权目录（幂等）
plan()         → { file, args, env?, capture }，exec 只负责 spawn
selfTest()     → 真跑一遍，验隔离也验能不能干活
dispose()      → 撤销授权，不留 ACL 债
```

| 后端 | 隔离原语 | 默认网络 |
| --- | --- | --- |
| `appcontainer` | Windows AppContainer 令牌 + 目录 ACL | 关闭（容器无 internetClient） |
| `bwrap` | mount namespace 白名单 + `--unshare-all` | 关闭（`--share-net` 才放行） |
| `docker` | 容器 + `--cap-drop ALL` + 同路径挂载 | 关闭（`--network none`） |

**输出捕获有两种模式**，由后端声明：`pipe`（直接继承管道，bwrap/docker 用）与 `files`（后端把 stdout/stderr 重定向到工作区 `.feima-tmp/`，exec 结束后读回，AppContainer 用）。后者是必要的：AppContainer 的子进程由启动器 `CreateProcess` 创建，是 Node 的"孙进程"，管道句柄第二次转发不可靠。

### 6.4 自检为什么是五件事

| 探针 | 验什么 |
| --- | --- |
| 读工作区诱饵 | 能不能干活 |
| 读宿主家目录诱饵**被拒** | 拦没拦住 |
| 写工作区 | 能不能干活 |
| 写宿主家目录**被拒** | 拦没拦住 |
| **列目录** | 能不能干活（且必须是独立进程里的 `dir`，不能用 cwd 句柄） |

第五项是踩出来的：前四项全绿、`dir` 全被拒，因为前四项访问的是已建立的 cwd 句柄，而 `dir` 要重新解析路径、逐级穿过上级目录。

### 6.5 命令白名单：为什么必须自己切段（v0.5）

白名单只在显式开启时生效（`--cmd-allow` / `FEIMA_CMD_ALLOW`），规则是 argv 前缀：

```
git status      → 放行 git status、git status --short
git             → 放行一切 git（写规则时要想清楚）
```

判断分两步，顺序不能反：

1. **先切段**。`splitCommands` 按 shell 语法把命令串切成若干段——`&&` `||` `;` `|` `&` 换行都是新命令的起点，双引号与单引号内的不切，双引号内的 `\"` 不结束引号。`git status; rm -rf ~` 因此变成两段，后半段单独过白名单。
2. **再匹配**。每段 `tokenize` 成 argv，与规则做前缀比较，任意一段不匹配就整体拒绝。

两类东西直接拒绝，不接受「规则里写全就行」：

- **命令替换**：`$( )`、反引号、`${ }`、`<( )`。替换出来的内容在校验之后才生成，白名单看不见它。
- **重定向**：`>` / `<`。它能把输出写到规则覆盖不到的地方。要写文件请用 `write_file`，那条路上有路径策略。

接在 `exec` 而不是 `bash` 工具里：工具会变多，而执行只有一个出口。

### 6.6 确认闸门的三个决定（v0.5）

**决定一：`write` 与 `exec` 是包含关系。** 能执行命令就能写文件，所以 `exec` 把写文件一起管住；反过来只开 `write` **挡不住** `bash "echo x > file"`。这一点在帮助文本与 README 里都写明了，没有用「包含关系」暗示「都管住了」。

**决定二：没有确认通道时默认拒绝。** `feima run` / `feima rpc` 没有 stdin 可以问。默认放行会让确认变成摆设（换个入口就全没了），所以默认拒绝，并把「加 `--yes` 才能放行、不要重试」写进工具结果告诉模型。

**决定三：`external` 无条件确认。** MCP 工具跑在策略层之外，飞码不知道它拿什么凭据、能访问什么。`--confirm off` 表示「我知道内置工具能干什么」，不表示「我允许一个我管不了的东西随便跑」。

确认的位置在**参数解析之后、工具执行之前**：提前问看不到参数，推后问等于先做了再问。

### 6.7 重试：判断依据是副作用，不是错误码（v0.5）

`withRetry` 只认两个回调：`isRetryable(err)` 与 `hasSideEffect()`。后者由循环层提供，因为只有那里看得见「这一轮吐过东西没有」：

```ts
let produced = false;   // 收到任何 text / reasoning / toolCall 就置 true
...
hasSideEffect: () => produced,
```

结果是这条策略比「429 重试三次」严格得多：**只有连不上、还没吐出第一个字节的失败才会重试**。理由很硬——流里已经吐了半句工具参数时重试，会把两截拼成一个谁也没写过的命令；正文已经上屏时重试，用户会看到同一段话两遍。

### 6.8 空转检测：判「有没有换思路」，不判「错得重不重」（v0.6）

位置：`src/core/repeat.ts`，挂在 `loop.runTool` 返回之后。它不做拦截，只做两件事：往工具结果里插一句提醒，或者在撞满阈值时结束这一轮。

三条判据，都只看形状不看语义：

| 判据 | 提醒 | 中止 | 抓的是什么 |
| --- | --- | --- | --- |
| 同一个失败原因 | 3 次 | 5 次 | 换了工具、换了写法，撞的是同一句话 |
| 同一个工具连续失败 | 3 次 | 5 次 | 命令换了、路径换了，每次都不成 |
| 完全相同的调用 | 4 次 | 8 次 | 名字与参数一模一样，结果不可能变 |

失败原因只取工具结果的第一行，并把数字抹平成 `N`——报错里常带耗时与行号，不归一化就永远数不到一起，而「同一堵墙」正是要抓的东西。

这套判据来自真机观测，不是设计出来的：模型被确认闸门拒绝之后，依次试了写文件工具、用 `bash` 调同一个工具、`echo` 重定向、两次用 shell 写文件，六次撞同一句「按拒绝处理」。`maxRounds` 拦不住这种情况——六次离上限还远，而真正的长任务需要几十轮。

**中止是「这一轮结束」，不是「进程退出」**：返回 `error`，会话、上下文、工具都还在，用户可以接着说话。中止与提醒都会发 `notice`，否则界面上看起来像模型莫名收尾。

### 6.9 已知边界（v0.3 明说）

- **AppContainer 需要祖先目录授权。** 容器的访问检查逐级进行，`D:\`、`D:\Documents` 默认没有给容器 SID 的 ACE。授权需要管理员权限，所以做成显式命令 `feima sandbox grant`，未授权时自检会失败并给出这条命令。
- **容器读不到 `%USERPROFILE%`。** 装在用户目录下的工具（node / git / python）默认不可用；目前只自动授权 `process.execPath` 所在目录，PortableGit 这类需要手工加。
- **策略层仍在生效**，隔离层不是它的替代品：命令策略拦的是"明显不该执行"的模式，隔离层拦的是"执行了也出不去"。
- **只拦"已知的破坏性模式"**，不是完备的命令白名单。

这些在 `doctor` 输出与 README 里都写明，不靠用户猜。

## 七、上下文压缩

位置：`AgentLoop.inner()` 每轮请求前，且必须在 `drainSteering()` **之后**。刚插进来的指令要留在保留区，否则会出现"用户刚说的事被摘要吃掉"。

流程：

```
估算 token（estimateMessages）
  ├─ 未超 budget → 什么都不做
  └─ 超预算
        ├─ 找切分点 cut
        │    ├─ 策略一：从尾部数 keepRecentTurns 个 user 消息（多轮对话的常态）
        │    └─ 策略二：找不到足够轮次时，从尾部按 keepTokens 保留（单轮长工具链）
        ├─ 折叠区 = messages[1..cut)
        ├─ 摘要（模型 → 失败降级规则摘要）
        ├─ 重建 = [system, 摘要, ...messages[cut..]]
        └─ 估算仍 >= 原来 → 放弃这次压缩
```

四条不变量：

1. `messages[0]`（system）永不进入折叠区；
2. `cut` 不能落在 `role === "tool"` 上。`assistant(tool_calls)` 与紧随的 `tool` 结果是一对，切在中间上游会直接 400；
3. 摘要消息本身不参与「用户轮次」计数，否则二次压缩会把切点算到摘要前面，折叠区只剩一条摘要，永远压不动；
4. 压缩结果必须更小，否则回退。

### 7.1 为什么需要两种切分策略

只按用户轮次切，在多轮对话里没问题；但「一轮任务里跑了 25 次工具调用」时，整条历史只有一条 user 消息，`keepRecentTurns=3` 永远找不到切分点，压缩一次都不会触发，上下文一路涨到上游报超长，而模型只会表现为「忘了前面读过什么」。

所以加了兜底：按轮次找不到切点，就从尾部往前累积 token，保留 `keepTokens`（默认取预算一半）的内容，切点右移到非 `tool` 的边界上，宁可多留一组工具结果也不切断配对。

两种策略的优先级是「轮次优先」：多轮对话里，用户说的话比按 token 算出来的边界更重要——把用户三句话之前的问题留在原文里，比留下三倍体积的工具输出有用。

摘要消息用 `role: "user"` 并带 `[上下文摘要` 前缀，二次压缩时按前缀识别旧摘要并合并，避免摘要套摘要丢信息。

事件 `compact` 只暴露 `before` / `after` / `folded` 三个数，不把摘要正文推给 UI——摘要属于内部状态，展示它会让用户误以为那是模型输出。

## 八、会话持久化

```
~/.feima/sessions/20261108-104117-yz8z.jsonl
  {"t":"meta","meta":{"v":1,"id":"...","title":"...","workspace":"...","model":"..."}}
  {"t":"msg","m":{...}}              ← 每条消息一条
  {"t":"compact","before":5612,"after":1180,"folded":8}
  {"t":"usage","u":{...}}
  {"t":"note","text":"reset"}
```

写入路径只有一条：`AgentLoop.push()` → `onRecord()` → `SessionStore.appendMessage()`。
不允许任何地方直接改 `messages` 数组，否则会出现"内存有、文件没有"。

恢复流程：

```
SessionStore.open(id) → load()（坏行跳过并计数）
  → loop.restore(messages)：丢弃旧 system，用当前配置重建
  → 打印横幅：条数、折叠次数、估算 token、跳过坏行数、最近 3 条诉求
```

损坏处理两种：

| 形态 | 处理 |
| --- | --- |
| 尾部半行（进程被 kill） | 读取时跳过；下次 append 前先补换行，防止新记录粘上去 |
| 整文件无 meta 行 | 不进 `sessions` 列表，`open` 时报"文件损坏" |

版本控制：`meta.v` 高于当前支持版本时拒绝打开，提示升级，不猜测字段含义。

## 九、RPC 协议

一行一条 JSON。请求带 `id`，响应同 `id`；事件单独成行。

```jsonc
// → 请求
{"id":"1","method":"prompt","params":{"text":"改一下配置"}}
// ← 回执（立即返回，表示已接受）
{"type":"response","id":"1","ok":true,"result":{"accepted":true}}
// ← 事件流
{"type":"event","event":{"type":"text_delta","text":"我先看看"}}
{"type":"event","event":{"type":"tool_start","name":"read_file","args":"{\"path\":\"src/config.ts\"}"}}
{"type":"event","event":{"type":"agent_settled"}}
// ← 本次任务结束（不带 id，和事件流区分开）
{"type":"response","id":null,"ok":true,"result":{"done":true,"outcome":"done"}}
```

方法：`prompt` / `steer` / `queue` / `abort` / `get_state` / `reset` / `usage` / `shutdown`。

**回执与结束分开**，是为了让 GUI 的"发送"按钮能立刻恢复，而不是等整轮结束。结束由 `agent_settled` 通知，状态由 `get_state` 确认。

## 十、后续演进

已经落地的（v0.3～v0.6）：真实隔离后端（AppContainer / bwrap / docker，可用性靠五项探针）、项目约定自动载入、飞链 RAG 检索工具、MCP 客户端与逐次确认、命令白名单、副作用确认、权限档、模型别名与压缩专用模型、离线冒烟脚本、真模型端到端验收、空转检测。

还没做的：

- **RPC 承载确认请求**：现在桌面端只能靠 `--yes` 或 `--mcp-allow` 预放行，确认框渲染不出来。要做成「宿主发 `confirm` 请求、前端弹窗、回 `confirm_result`」的双向协议，这属于 v1.0 的前置工作。
- **端到端记录化**：现在 e2e 只回答「这次成不成」，不记录轮次、token、工具成功率、撞墙次数，也就没有趋势可比。
- **macOS 原生后端**（`sandbox-exec`）：目前走 docker。
- **容器内 git / python 的自动授权链**：AppContainer 只授权了 node 所在目录。
- **会话索引**：超过数百个会话时再上，接口已收敛在 `SessionStore`。

关于「模型端到端」这条：v0.6 已经补上（本机 Ollama + `npm run e2e`），它给出的结论是——8B 的本地模型足以跑通读→改→测闭环，但被策略拒绝之后会本能地换写法重试，所以错误信息的措辞与空转检测都是必需品。
