# 架构

## 一、分层

```
┌─────────────────────────────────────────────┐
│ 接入层                                       │
│   CLI（交互 / run --json）   RPC 宿主（JSONL）│
└───────────────┬─────────────────────────────┘
                │ AgentEvent（单向事件流）
┌───────────────▼─────────────────────────────┐
│ 循环层  AgentLoop                            │
│   内层：模型 → 工具 → 模型（含插话）          │
│   外层：追加任务（follow-up）                 │
│   旁挂：Compact（超预算折叠） Session（落盘） │
└───────┬───────────────────────┬─────────────┘
        │                       │
┌───────▼──────────┐   ┌────────▼─────────────┐
│ 模型层 Provider   │   │ 工具层 Tools          │
│ OpenAI 兼容 + SSE │   │ 7 个内置，走 ToolContext │
└──────────────────┘   └────────┬─────────────┘
                                │
                       ┌────────▼─────────────┐
                       │ 安全层 Sandbox       │
                       │ 策略：路径/环境/命令  │
                       │ 执行：spawn + 超时    │
                       │ 握手：token 校验      │
                       └──────────────────────┘
```

约束：**跨层只能单向调用**。工具层不许自己 `spawn`，接入层不许直接读文件，模型层不许知道工作区在哪。

## 二、双循环

### 2.1 内层（推进任务）

```
while 轮次 < maxTurns:
    把排队的插话并入上下文
    请求模型（流式）
    出错 / 被取消 → 结束本次运行，交由上层决定是否重试
    有工具调用：
        如果 finish_reason === "length"：参数可能被截断 → 不执行，回灌错误让模型重发
        否则逐个执行，把结果并入上下文
    没有工具调用：
        还有插话 → 继续循环
        没有插话 → 内层结束
```

### 2.2 外层（接续任务）

内层自然结束后，检查 follow-up 队列。有就作为新的 user 消息再来一轮，没有才算这次运行结束。

### 2.3 为什么插话和追加要分开

- 插话（steering）是**改变当前任务**：用户看到 Agent 跑偏了，说"别动那个文件"。它必须在**下一次请求模型之前**进入上下文。
- 追加（follow-up）是**任务完成后的下一步**："顺便把测试也跑了"。它不该打断当前任务。

混成一队，就会出现"用户中途纠正了一句，结果被排到整个任务结束才生效"。

## 三、状态机

唯一权威：`snapshot.isStreaming`。

```
idle ──submit──▶ chatting ──(无工具调用 & 无插话)──▶ idle
                    │                                ▲
                    └── error / aborted ─────────────┘
```

要点：

1. **不用事件判定结束**。`turn_end` 只代表一轮结束，之后可能还有追加任务；收到 `agent_end` 后仍可能发生重试或上下文压缩。
2. **`agent_settled` 的语义是"已确认空闲"**，发出时 `isStreaming` 必须已经是 `false`。测试里对这一点有断言。
3. **置位先于 await**。`submit()` 第一行就判断并置位，否则同一 tick 的第二次提交会读到旧状态，被当成新任务而不是插话。

## 四、模型层

- 只支持 OpenAI 兼容的 `/chat/completions`，流式。国产模型（DeepSeek / Qwen / GLM / Kimi / MiniMax）与聚合网关（OpenRouter、MixRoute、百炼、方舟）都能直接接。
- SSE **只按 `\n` 切**。行内可能夹带超长 JSON，用 `readline` 解析会让工具调用参数错位。
- 工具调用按 `index` 拼装，`id` 缺失时补一个稳定值，避免上游不规范导致消息不合法。
- 报错先脱敏再抛出，并标注 `retryable`（429/5xx 可重试，4xx 不可）。

---

## 五、工具层

`Tool` 接口三件套：`name` / `description` / `parameters`（JSON Schema）+ `run(args, ctx)`。

- 参数一律手动校验并给出人话错误，不引 zod（零依赖原则）。
- 所有路径先进 `resolveRead` / `resolveWrite`，再碰 `fs`。
- 输出截断：读文件 1MB 上限、命令输出 256KB 上限、grep 300 条上限。上下文是稀缺资源，宁缺毋滥。
- 命令统一走 `ctx.exec`，工具层拿不到 `child_process`。

## 六、安全层

### 6.1 五层机制

| 层 | 实现 | 防什么 |
| --- | --- | --- |
| 路径围栏 | `realpathLoose` + `isInside` | `../`、符号链接穿越（`workspace/link -> /etc`） |
| 读写黑名单 | denyRead 7 项 / denyWrite 6 项 | 凭据文件、`.env`、`.git/hooks` 持久化、`.agents`/`.codex` 横向移动 |
| 环境变量白名单 | 正则放行 16 类，强制 `TERM=dumb` | 子 shell 一句 `env` 打印出所有 API Key |
| 命令策略 | `guardCommand` 正则拦截 | `rm -rf /`、`mkfs`、强推、`curl \| sh`、fork 炸弹 |
| 握手 + 失败即阻断 | 受控命令带回随机 token，20s 超时 | "扩展加载成功但没生效"的假绿 |

### 6.2 为什么 `.git/hooks` 要单独拦

git 进程在沙盒外。Agent 只要写一个 `pre-commit`，下次提交时就能执行任意代码，**完全绕过**所有隔离设计。这不是越权读写，是沙盒逃逸。

同理 `.agents` / `.codex`：用 A 的沙盒去改 B 的规则，是典型的横向移动。

### 6.3 隔离后端（v0.3）

`policy` 模式下进程本身没有沙箱，只有入口被策略过滤。`strict` 要的是另一件事：**即使命令绕过了所有正则，它也碰不到工作区之外的东西**。

实现靠三个后端，契约在 `src/safety/isolation.ts`：

```
availability() → 能不能用，不能用的原因（要具体到能动手修）
prepare()      → 建 profile、授权目录（幂等）
plan()         → { file, args, env?, capture }，exec 只负责 spawn
selfTest()     → 真跑一遍，验隔离也验能不能干活
dispose()      → 撤销授权，不留 ACL 债
```

| 后端 | 隔离原语 | 默认网络 |
| --- | --- | --- |
| `appcontainer` | Windows AppContainer 令牌 + 目录 ACL | 关闭（容器无 internetClient） |
| `bwrap` | mount namespace 白名单 + `--unshare-all` | 关闭（`--share-net` 才放行） |
| `docker` | 容器 + `--cap-drop ALL` + 同路径挂载 | 关闭（`--network none`） |

**输出捕获有两种模式**，由后端声明：`pipe`（直接继承管道，bwrap/docker 用）与 `files`（后端把 stdout/stderr 重定向到工作区 `.feima-tmp/`，exec 结束后读回，AppContainer 用）。后者是必要的：AppContainer 的子进程由启动器 `CreateProcess` 创建，是 Node 的"孙进程"，管道句柄第二次转发不可靠。

### 6.4 自检为什么是五件事

| 探针 | 验什么 |
| --- | --- |
| 读工作区诱饵 | 能不能干活 |
| 读宿主家目录诱饵**被拒** | 拦没拦住 |
| 写工作区 | 能不能干活 |
| 写宿主家目录**被拒** | 拦没拦住 |
| **列目录** | 能不能干活（且必须是独立进程里的 `dir`，不能用 cwd 句柄） |

第五项是踩出来的：前四项全绿、`dir` 全被拒，因为前四项访问的是已建立的 cwd 句柄，而 `dir` 要重新解析路径、逐级穿过上级目录。

### 6.5 已知边界（v0.3 明说）

- **AppContainer 需要祖先目录授权。** 容器的访问检查逐级进行，`D:\`、`D:\Documents` 默认没有给容器 SID 的 ACE。授权需要管理员权限，所以做成显式命令 `feima sandbox grant`，未授权时自检会失败并给出这条命令。
- **容器读不到 `%USERPROFILE%`。** 装在用户目录下的工具（node / git / python）默认不可用；目前只自动授权 `process.execPath` 所在目录，PortableGit 这类需要手工加。
- **策略层仍在生效**，隔离层不是它的替代品：命令策略拦的是"明显不该执行"的模式，隔离层拦的是"执行了也出不去"。
- **只拦"已知的破坏性模式"**，不是完备的命令白名单。

这些在 `doctor` 输出与 README 里都写明，不靠用户猜。

## 七、上下文压缩

位置：`AgentLoop.inner()` 每轮请求前，且必须在 `drainSteering()` **之后**。刚插进来的指令要留在保留区，否则会出现"用户刚说的事被摘要吃掉"。

流程：

```
估算 token（estimateMessages）
  ├─ 未超 budget → 什么都不做
  └─ 超预算
        ├─ 找切分点 cut
        │    ├─ 策略一：从尾部数 keepRecentTurns 个 user 消息（多轮对话的常态）
        │    └─ 策略二：找不到足够轮次时，从尾部按 keepTokens 保留（单轮长工具链）
        ├─ 折叠区 = messages[1..cut)
        ├─ 摘要（模型 → 失败降级规则摘要）
        ├─ 重建 = [system, 摘要, ...messages[cut..]]
        └─ 估算仍 >= 原来 → 放弃这次压缩
```

四条不变量：

1. `messages[0]`（system）永不进入折叠区；
2. `cut` 不能落在 `role === "tool"` 上。`assistant(tool_calls)` 与紧随的 `tool` 结果是一对，切在中间上游会直接 400；
3. 摘要消息本身不参与「用户轮次」计数，否则二次压缩会把切点算到摘要前面，折叠区只剩一条摘要，永远压不动；
4. 压缩结果必须更小，否则回退。

### 7.1 为什么需要两种切分策略

只按用户轮次切，在多轮对话里没问题；但「一轮任务里跑了 25 次工具调用」时，整条历史只有一条 user 消息，`keepRecentTurns=3` 永远找不到切分点，压缩一次都不会触发，上下文一路涨到上游报超长，而模型只会表现为「忘了前面读过什么」。

所以加了兜底：按轮次找不到切点，就从尾部往前累积 token，保留 `keepTokens`（默认取预算一半）的内容，切点右移到非 `tool` 的边界上，宁可多留一组工具结果也不切断配对。

两种策略的优先级是「轮次优先」：多轮对话里，用户说的话比按 token 算出来的边界更重要——把用户三句话之前的问题留在原文里，比留下三倍体积的工具输出有用。

摘要消息用 `role: "user"` 并带 `[上下文摘要` 前缀，二次压缩时按前缀识别旧摘要并合并，避免摘要套摘要丢信息。

事件 `compact` 只暴露 `before` / `after` / `folded` 三个数，不把摘要正文推给 UI——摘要属于内部状态，展示它会让用户误以为那是模型输出。

## 八、会话持久化

```
~/.feima/sessions/20261108-104117-yz8z.jsonl
  {"t":"meta","meta":{"v":1,"id":"...","title":"...","workspace":"...","model":"..."}}
  {"t":"msg","m":{...}}              ← 每条消息一条
  {"t":"compact","before":5612,"after":1180,"folded":8}
  {"t":"usage","u":{...}}
  {"t":"note","text":"reset"}
```

写入路径只有一条：`AgentLoop.push()` → `onRecord()` → `SessionStore.appendMessage()`。
不允许任何地方直接改 `messages` 数组，否则会出现"内存有、文件没有"。

恢复流程：

```
SessionStore.open(id) → load()（坏行跳过并计数）
  → loop.restore(messages)：丢弃旧 system，用当前配置重建
  → 打印横幅：条数、折叠次数、估算 token、跳过坏行数、最近 3 条诉求
```

损坏处理两种：

| 形态 | 处理 |
| --- | --- |
| 尾部半行（进程被 kill） | 读取时跳过；下次 append 前先补换行，防止新记录粘上去 |
| 整文件无 meta 行 | 不进 `sessions` 列表，`open` 时报"文件损坏" |

版本控制：`meta.v` 高于当前支持版本时拒绝打开，提示升级，不猜测字段含义。

## 九、RPC 协议

一行一条 JSON。请求带 `id`，响应同 `id`；事件单独成行。

```jsonc
// → 请求
{"id":"1","method":"prompt","params":{"text":"改一下配置"}}
// ← 回执（立即返回，表示已接受）
{"type":"response","id":"1","ok":true,"result":{"accepted":true}}
// ← 事件流
{"type":"event","event":{"type":"text_delta","text":"我先看看"}}
{"type":"event","event":{"type":"tool_start","name":"read_file","args":"{\"path\":\"src/config.ts\"}"}}
{"type":"event","event":{"type":"agent_settled"}}
// ← 本次任务结束（不带 id，和事件流区分开）
{"type":"response","id":null,"ok":true,"result":{"done":true,"outcome":"done"}}
```

方法：`prompt` / `steer` / `queue` / `abort` / `get_state` / `reset` / `usage` / `shutdown`。

**回执与结束分开**，是为了让 GUI 的"发送"按钮能立刻恢复，而不是等整轮结束。结束由 `agent_settled` 通知，状态由 `get_state` 确认。
