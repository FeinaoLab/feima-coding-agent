## 一、为什么做

### 1.1 直接动因

对 `inkwellio/my-coding-agent` 做源码级拆解后，得到一个明确结论：**这个项目值钱的不是那个 Electron 壳，而是三个东西**——Agent 双循环、以 `isStreaming` 为准的状态机、五层安全边界。壳的部分一个月能有人抄出来，这三件事抄不明白就会在真实使用中反复出问题：

- 见 `agent_end` 就熄灯，结果模型在重试或压缩上下文，界面"答完了"又跳起来；
- 沙盒"看起来开了"，实际扩展加载成功但命令没被隔离；
- 沙盒只封 `bash`，Windows 上的 PowerShell 还是通的；只封 Agent 的工具，用户手敲的命令还是通的。

飞码立项的第一目的就是：**先把这三件事做对，再谈界面。**

### 1.2 自身需求

现有工具在中文场景下有三个不适配：

1. 提示词与交互是全英文的，输出经常夹生；
2. 国内模型（DeepSeek、Qwen、GLM、Kimi、MiniMax）接入要自己改配置，各家工具调用格式还有差异；
3. 想接自己的知识库（飞链 RAG）做检索增强，没有插口。

### 1.3 时机

Node 22.6+ 自带 TS 类型擦除，可以做到**零构建、零运行时依赖**发布一个 Agent。这意味着维护成本极低，也意味着不需要为"框架"付出学习与升级代价。

## 二、目标与非目标

### 2.1 v0.1 目标（已完成）

| 编号 | 目标 | 验收 |
| --- | --- | --- |
| G1 | 双循环 Agent：内层工具链 + 插话，外层追加任务 | 单测覆盖 4 种路径，18 用例全绿 |
| G2 | 状态机以 `isStreaming` 为唯一权威 | `agent_settled` 触发时 `isStreaming===false`，有断言 |
| G3 | 并发安全：运行中提交自动降级为插话 | 有专门用例，验证不会并发跑两轮 |
| G4 | 五层安全边界：路径/写入/环境变量/命令/握手 | 符号链接、`.git/hooks`、env 泄漏均有测试 |
| G5 | 零运行时依赖 | `dependencies: {}`，`node_modules` 为空可运行 |
| G6 | 三种接入方式：CLI 交互、单次执行、RPC | `feima` / `feima run` / `feima rpc` 均实测 |

### 2.2 明确不做（v0.1）

- **不做 GUI**。桌面端是 v1.0，且必须复用 `feima rpc`，不允许在渲染层重写引擎。
- **不做多 Agent 编排**。子 Agent、任务分派是另一个问题域，会污染循环的清晰度。
- **不做 MCP**。MCP 工具的风险面与内置工具不同（外部进程、外部网络），要单独设计确认机制，不是加个 adapter 就完事。
- **不做真实的进程级隔离**（v0.3 已推翻这条，见 M3）。v0.1 只有策略层；`strict` 模式在没有隔离后端时直接拒绝执行命令，这是刻意的失败即阻断。

### 2.3 成功标准

不是"能跑通 demo"，而是：

1. 用本地 qwen3:8b 也能完成一次「读文件 → 改文件 → 跑测试」的完整闭环；
2. 把工作区指向一个陌生仓库，Agent 无法写出工作区，也无法读到 `~/.ssh`；
3. 拔掉 API Key 或模型服务 500 时，CLI 给出可读错误而不是堆栈，且状态回到 idle。

## 三、关键决策

| 决策 | 选项 | 结论与理由 |
| --- | --- | --- |
| 引擎 | 复用 `pi-coding-agent` / 自研 | **自研**。要中文优化、要接飞链 RAG、要零依赖；代价是流式拼装与工具协议自己写，约 400 行，已跑通 |
| 语言 | TypeScript（构建）/ TypeScript（擦除运行） | **擦除运行**。Node 22.6+ 直接跑 `.ts`，省掉构建链；代价是不能用 enum / namespace / 参数属性 |
| 界面 | CLI 先行 / Electron 先行 | **CLI 先行**。引擎没稳之前做 GUI，等于把 bug 藏进渲染层 |
| 隔离 | 引入 srt / 只做策略 | **策略优先，接口预留**。srt 在 Windows 仍是 alpha，先保证路径与 env 两条最常被利用的通道关死 |
| 配置 | 全环境变量 / 配置文件 + 环境变量 | **两者都支持**，环境变量优先，便于 CI |
| 协议 | 自定 JSON / JSONL | **JSONL**。一行一条，能直接 `tail -f`，也能被任何语言消费 |

### 3.1 与参考实现的差异（有意为之）

| 维度 | 参考实现 | 飞码 v0.1 |
| --- | --- | --- |
| 分发 | Electron 安装包，随包带 Node | 单仓库，Node ≥ 22.6 直接跑 |
| 引擎 | `@earendil-works/pi-coding-agent` | 自研，无外部依赖 |
| 隔离 | `@anthropic-ai/sandbox-runtime` 锁 0.0.78 | 策略层 + 预留后端接口，`strict` 失败即阻断 |
| 状态 | `get_state.isStreaming` | 同思路，`AgentLoop.getSnapshot()` |
| 工具协议 | Pi 的扩展机制 | 自带 7 个工具，`Tool` 接口对外可扩展 |
| 中文 | 无特殊处理 | 提示词、错误、CLI 全中文 |

## 五、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 自研引擎在真实仓库上暴露长尾问题（工具参数截断、上下文爆炸） | 可用性 | 已有截断回灌机制；M2 加压缩与摘要；每次回归用固定仓库跑冒烟 |
| 隔离后端"检测到"不等于"能用"（内核开关、命名空间权限、ACL 授权都可能让沙盒形同虚设） | 安全 | 可用性靠真跑：`selfTest` 五项探针，否定项必须在沙盒能正常执行的前提下才算数；`strict` 下自检不过拒绝启动 |
| 隔离后端在部分环境不可用（祖先目录 ACL 需管理员、Windows 上装在用户目录的 git/PortableGit 读不到） | 可用性 | `doctor` 逐项打印探针结果并给出修复命令；`feima sandbox grant` 是唯一会改系统状态的显式入口 |
| 国产模型的工具调用格式不统一 | 兼容 | Provider 只认 OpenAI 格式；差异在 provider 层做适配，不进循环 |
| 中文提示词导致模型过度解释 | 体验 | 提示词要求"报告具体、不写空话"，后续用真实任务回归调 |
| 依赖 Node 22.6+ | 装机门槛 | README 与 `engines` 明确；必要时补一个 esbuild 打包版 |

## 六、协作与规范

- 仓库规范见 `AGENTS.md`（可判定、可执行，不写"请注意整洁"）。
- 变更记录见 `CHANGELOG.md`，每条必须写清"现象 / 根因 / 修法"。
- 提交格式：`类型: 简短描述`（feat / fix / docs / test / chore）。
- 测试：`node --test tests/*.test.ts`，涉及文件系统的一律用临时目录。
