## ADR-001 自研引擎，不复用 pi-coding-agent

**日期**：2026-11-08　**状态**：生效

**背景**：参考实现 `inkwellio/my-coding-agent` 用的是 `@earendil-works/pi-coding-agent`，引擎能力完整，直接复用能省两周。

**候选**：

1. 复用 pi-coding-agent，只做壳与适配；
2. 自研循环与工具协议。

**决定**：自研。约 320 行的 `core/loop.ts` 承担全部循环逻辑。

**理由**：

- 三个必须改的点都在引擎内部：状态权威（`isStreaming` 的时序）、插话与追加的双队列语义、压缩触发点。用别人的引擎改这三处，等于 fork，后续上游一升级就要重新对齐。
- 要接飞链 RAG 做检索增强，需要在「工具调用前」插入自己的检索决策，外部引擎没有这个钩子。
- 引擎是这类产品的核心资产，不是可替换的依赖。

**代价**：SSE 解析、工具调用片段拼装、增量 JSON 容错都得自己写，这部分在 `providers/openai.ts` 里约 190 行；上游模型的协议差异也要自己适配。

**什么时候该推翻**：如果要支持 Anthropic 原生协议、多模态、prompt caching 这类引擎级能力，自研成本会超过收益，届时应改为 fork + 定期同步上游。

## ADR-002 零运行时依赖，Node 类型擦除直跑 TS

**日期**：2026-11-08　**状态**：生效

**背景**：目标是给团队内和自己长期用，装机摩擦要尽可能低。

**候选**：

1. 常规 TS 工程：`tsc` 构建 + `node_modules`；
2. `esbuild` 打包成单文件；
3. Node ≥ 22.6 的类型擦除，源码直接运行。

**决定**：方案 3。

**理由**：`dependencies` 为空意味着没有供应链风险、没有 `npm audit`、没有版本地狱，改一行代码立刻生效，调试时看到的行号就是源码行号。

**代价（很具体）**：

- 不能用 `enum`、`namespace`、装饰器、构造函数参数属性；
- 类型导入必须写 `import type`（`verbatimModuleSyntax` 要求），否则运行时找不到导出；
- 类型错误不会被拦住——`node` 只擦除不检查，`npm run typecheck` 需要另装 typescript，默认不跑。所以**测试必须比类型检查更密**，这是 38 个用例存在的直接原因。

## ADR-003 CLI 先行，GUI 只做 RPC 客户端

**日期**：2026-11-08　**状态**：生效

**背景**：参考实现是 Electron 桌面端，视觉上更像成品。

**候选**：Electron 先行 / CLI 先行 / 同时做。

**决定**：CLI 先行，桌面端在 v1.0，且**只允许**通过 `feima rpc` 驱动引擎。

**理由**：引擎没稳定时做 GUI，等于把并发、状态、错误处理的问题藏进渲染层——那里最难测、最容易掩盖。RPC 边界强制把「引擎」和「界面」分开，引擎的每个能力都能在没有 UI 的情况下被验证。

**代价**：早期没有可展示的界面；RPC 协议要先定下来，后期改协议的成本高于改内部函数。

## ADR-004 v0.1 只做策略层隔离，strict 失败即阻断

**日期**：2026-11-08　**状态**：生效

**背景**：`@anthropic-ai/sandbox-runtime` 在 Windows 上是 alpha，锁定版本仍有不确定性。

**候选**：

1. 直接引入 srt，赌它可用；
2. 只做策略层（路径、环境、命令过滤），预留后端接口；
3. 不做隔离，先跑起来。

**决定**：方案 2。`--sandbox strict` 在检测不到隔离后端时**直接拒绝执行命令**，不静默降级。

**理由**：安全承诺最怕「看起来开了」。策略层能关掉两条最常被利用的通道（路径穿越、环境变量泄漏），成本低且确定性高；真实隔离留接口，等 Windows Job Object 或 Linux namespace 后端就位再开。

**代价**：`policy` 模式下的命令仍有真实系统权限，只能靠命令过滤兜底。这一点在 `doctor` 和启动横幅里明示，不靠用户猜。

## ADR-005 `isStreaming` 作为唯一状态权威

**日期**：2026-11-08　**状态**：生效

**背景**：源码实证里提到，参考实现在 `agent_end` 之后仍可能发生重试和上下文压缩，界面若见到结束事件就熄灯，会出现「答完了又跳起来」。

**决定**：所有结束判断只读 `snapshot.isStreaming`；`agent_settled` 事件必须在状态已落回 `idle` 之后才发出。

**实现约束**：`submit()` 里先 `busy=false; state="idle"` 再 `emit("agent_settled")`，顺序不能反；有专门用例断言「settled 时 isStreaming === false」。

**代价**：事件不再自解释，UI 收到任何事件都要回头查一次快照。多一次调用，换来状态不可能错。

## ADR-006 上下文压缩用摘要，切分点只落在 user

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：v0.1 没有压缩，长会话会顶到模型上限；一旦超限，上游报错或悄悄丢历史，表现是「刚看过的文件又问一遍」。

**候选**：

1. 滑动窗口，直接丢最早的 N 条；
2. 把早期消息交给模型摘要，替换成一条摘要消息；
3. 检索式记忆（把历史当向量库，按需召回）。

**决定**：方案 2；方案 1 作为摘要不可用时的降级；方案 3 留到接入飞链 RAG 时再做。

**理由**：

- 直接丢会丢掉「用户最初的目标」和「改了哪些文件」，这两类信息一旦丢了，后续所有操作都可能在错误前提上继续。
- 摘要能保留结论与路径，成本是一次额外模型调用。
- 检索式记忆最省 token，但要向量库和嵌入模型，会把零依赖这条打破，等 RAG 接入时一并做。

**三条硬约束（写进代码注释与测试）**：

1. **系统提示永不折叠**。它定义行为边界，摘要成一句话就丢掉了约束力。
2. **切分点只能落在 `user` 消息上**。`assistant(tool_calls)` 和紧随的 `tool` 结果是一对，切在中间上游会直接报 400（找不到对应的 `tool_call_id`）。
3. **压缩必须真的变小**，否则放弃本次压缩。否则出现「越压越长」的荒谬情况。

**降级链**：模型摘要 →（失败）规则摘要 →（还不够小）不压缩。规则摘要只列用户诉求、调用过的工具、最后几条结论，绝不编造。

**代价**：压缩本身要一次模型调用，短会话压缩不划算，所以设了「可折叠内容不足 3 条就不压」的门槛；摘要必然有损，重要细节靠模型重新读取文件来找回。

## ADR-007 会话用 JSONL append-only，存 `~/.feima`

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：v0.1 退出即丢历史，长任务中断后只能重来。

**候选**：

1. 单个 JSON 文件，每次全量写入；
2. SQLite；
3. JSONL append-only，一行一条记录。

**决定**：方案 3，目录 `~/.feima/sessions/`，文件名 `<时间戳>-<随机4位>.jsonl`。

**理由**：

- **崩溃安全**：进程被 kill 时最多丢最后半行，前面的历史完整可读；全量写 JSON 则整个文件可能变成半截，一条都读不回来。
- **可观测**：`tail -f` 就能看 Agent 在做什么，不需要查看器。
- **可演进**：新增记录类型（压缩、用量、备注）只是多一种行，旧版本读到不认识的类型跳过即可。
- **不写工作区**：会话里有敏感路径和业务信息，放仓库里容易被误提交；跨项目检索时按 `meta.workspace` 过滤。

**实现细节（都是踩过的坑）**：

- append 前检查文件末尾是否以 `\n` 结束，不是就先补一个。否则新记录会粘到残行后面，把两条都变成坏行。
- 读取时坏行跳过并计数，恢复横幅会提示「跳过 N 行损坏记录」。
- 首条用户消息自动成为标题，并**重写第一行 meta**。只改内存会导致列表里永远显示「未命名会话」。
- 恢复时系统提示用**当前配置重新生成**，不沿用会话里那条——工作区变了、提示词改了，旧约束带回来是负担。

**代价**：没有索引，`list` 要扫目录读每人的首行；会话多了会慢（几百个以内无感）。真要做检索再上 SQLite，接口已经收敛在 `SessionStore` 里。

## ADR-008 压缩预算用字符估算，不引入 tokenizer

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：判断「该不该压缩」需要一个 token 数。

**候选**：

1. 引入 `tiktoken` / 模型自带 tokenizer，精确计数；
2. 按字符估算：中日韩 1.05 token/字，其他 3.6 字符/token。

**决定**：方案 2。

**理由**：tokenizer 是几十 MB 的原生依赖，且不同厂商分词器不同，为了一个「是否压缩」的阈值引入它不划算。估算误差在 15% 以内，只要阈值留足余量（32k 上下文按 22000 触发）就不会误判。

**代价**：真实计费以 `usage` 为准，估算值不能用来算钱；`/context` 显示的是近似值，标注为「约」。

**什么时候该推翻**：如果要做「精确预算分配」（比如按剩余额度决定压缩多少轮），估算精度不够，届时按 provider 引入对应 tokenizer。

## ADR-009 压缩切分点：轮次优先，token 兜底

**日期**：2026-11-08　**状态**：生效（v0.2.1）

**背景**：v0.2.0 的切分点只按「从尾部数第 N 个 user 消息」算。做长任务验收时发现一个致命空档：**一轮任务里跑了 25 次工具调用，整条历史只有一条 user 消息，`findCut` 返回 -1，压缩一次都不会触发。** 上下文从 3k 一路涨到上游上限，模型开始反复读同一个文件——不报错，只是变笨。这条在 v0.2.0 的遗留清单里写着「单轮内超长工具链不中途压」，实际比预想的严重：不是「压得不够勤」，是「完全不压」。

**候选**：

1. 固定保留最近 K 条消息，按条数切；
2. 只按 token 切：从尾部累积到 `keepTokens` 为止；
3. 双策略：有足够用户轮次时按轮次切，否则按 token 切。

**决定**：方案 3。

**理由**：

- 方案 1 在「一条消息 5 万字符」时完全失效——留 10 条也可能是 8 万 token。
- 方案 2 会切掉用户最近的诉求。多轮对话里，用户三句话之前说的约束，比三倍体积的工具输出更重要；纯 token 切法不看语义边界，容易把「把版本改成 0.2.0」这种关键指令折进摘要。
- 方案 3 保留了两种场景各自的最优解：多轮对话看轮次，单轮长链看 token。

**实现约束**（比策略本身更容易出错）：

- 切点不能落在 `tool` 消息上，否则 `assistant(tool_calls)` 被折走、结果还在，上游直接 400。落到 tool 上就右移到整组结束，宁可多留。
- 摘要消息是 `role: "user"`，必须排除在轮次计数之外。否则第二次压缩会把切点算到摘要前面，折叠区只剩一条摘要，触发「可折叠内容不足」，压缩永久停滞。
- 压缩后必须真的更小，否则回退——`keepTokens` 设得过大时会命中这条保护。

**代价**：多一个配置项（`keepTokens` / `FEIMA_KEEP_TOKENS`），多一个分支。两种策略的交互需要专门的用例守：长工具链测试（配对完整性）、连续三次压缩（摘要不累积）。

**什么时候该推翻**：如果接入按「任务」划分的结构化历史（把一轮任务显式切成阶段），切分点应该由阶段边界决定，而不是靠轮次或 token 猜。

## ADR-010 隔离后端：平台原生优先，容器兜底，可用性靠探针而非检测

**日期**：2026-11-08　**状态**：生效（v0.3.0）

**背景**：v0.1 到 v0.2 的 `strict` 模式是个空壳——它在文档里写着"需要隔离后端"，代码里直接拒绝所有命令。真正的隔离需要一个能在普通开发机上跑起来的东西，而不是一句"请自行安装沙盒"。

**候选**（Windows / Linux / macOS 分别考虑）：

| 方案 | 前提 | 文件系统隔离 | 结论 |
| --- | --- | --- | --- |
| Windows Sandbox | Pro/Enterprise + 重启 | 有（整机虚拟机） | 否：太重，且是一个独立桌面 |
| Hyper-V 容器 | daemon + 管理员 | 有 | 否：环境前提太多 |
| Docker / WSL | daemon 或内核组件 | 有 | 作为兜底 |
| AppContainer | 无，系统自带 | 有（内核级 ACL） | Windows 主路径 |
| bubblewrap | 内核允许非特权 user namespace | 有（mount namespace） | Linux 主路径 |
| macOS sandbox-exec | 系统自带 | 有（seatbelt） | 未实现，走 docker |

**决定**：实现一个 `IsolationBackend` 契约（`availability / prepare / plan / selfTest / dispose`），提供 `appcontainer`、`bwrap`、`docker` 三个实现，`auto` 按平台优先级挑，兜底 `none`。

**理由**：

- 三个平台的隔离原语完全不同，但上层只需回答一个问题：**这条命令要交给谁去 spawn**。`plan()` 返回 `{file, args}`，exec 只负责 spawn 与收输出，其余全在各自后端里。
- 不追求"一个后端通吃"。Windows 上没有轻量对等物，硬凑（比如把 docker 塞进 Windows 路径）会让工具返回的路径与宿主不一致，模型拿着容器内路径拼下一条命令就找不到文件。所以 docker 后端明确只做**同路径挂载**，Windows 上直接报不可用。

**关键约束（都是踩出来的）**：

1. **`DeriveAppContainerSidFromAppContainerName` 对未注册的 profile 也会返回 SID。** 先 Derive 再 Create 的顺序会让 profile 从未真正注册，拿到的 SID 去 `CreateProcess` 只得到一句 `failed: 2`。必须先 Create，再在 `ERROR_ALREADY_EXISTS` 时 Derive。
2. **`CreateProcess` 的 `lpApplicationName` 必须留 NULL。** 显式传 `C:/Windows/System32/cmd.exe` 在 AppContainer 令牌下会返回 `ERROR_FILE_NOT_FOUND`；让加载器按 PATH 自己搜反而正常。
3. **从 MSYS/Git Bash 启动时 `process.env.PATH` 不含 System32**，只有一串 `/c/...` 的 POSIX 路径。不归一化的话，容器里连 `cmd.exe` 都找不到。
4. **环境变量名大小写不敏感，但 JS 对象不是。** 基础环境里是 `Path`，后端补的是 `PATH`，两个键并存时 spawn 会传出两个条目，取哪个看运气。合并时必须按大小写去重。
5. **AppContainer 需要 `LOCALAPPDATA` 才能定位自己的 LocalState 目录**，缺了返回 `ERROR_ENVVAR_NOT_FOUND(203)`，错误信息与"缺目录变量"毫无关联。
6. **`cmd.exe` 启动时会主动 `cd` 到 `HOMEDRIVE+HOMEPATH`。** 指向用户目录就会立刻「拒绝访问」，之后所有命令都在错误的目录里跑。
7. **祖先目录的 ACE 是硬要求。** AppContainer 的访问检查逐级进行，`D:/`、`D:/Documents` 默认都没有给容器 SID 的 ACE；哪怕目标目录给了完全控制，`cd` 和 `dir` 仍然被拒。修改这些目录需要管理员权限，非提权时 `icacls` 会挂起等 UAC。因此这一步做成显式命令 `feima sandbox grant`，不在启动路径里赌。
8. **`chcp 65001 >nul` 在容器里失败**（打不开 NUL 设备），报错会混进每条命令的 stderr。改成写工作区里的辅助文件。

**代价**：多一个后端抽象层、三份 `plan()` 参数拼装、一个 `sandbox grant` 命令。Windows 上 strict 模式的实际可用性取决于用户是否愿意授权祖先目录——这是操作系统的事实限制，不是实现缺陷，所以要在 `doctor` 里说清楚，而不是假装能用。

**什么时候该推翻**：如果 Windows 上出现"随进程分配的轻量文件系统沙盒"（比如系统级 API 支持按进程挂载只读视图），就不需要动 ACL；届时 `appcontainer` 后端应整体替换，而不是打补丁。

## ADR-011 可用性判定：探针必须验"能不能干活"，不只是"拦没拦住"

**日期**：2026-11-08　**状态**：生效（v0.3.0）

**背景**：第一版 `selfTest` 只验四件事：读工作区诱饵、读宿主家目录诱饵被拒、写工作区、写宿主家目录被拒。四项全绿，`doctor` 于是判定"隔离可用"。

然后真机一跑，`dir` 全被拒。**能 `type` 单个文件、能 `echo` 写文件，但列不了目录**——因为路径解析要逐级穿过上级目录，而上层没授权。四个探针一个都没发现：它们用的都是已经建立的 cwd 句柄，绕过了路径解析。

**决定**：`selfTest` 增加第五项 `listWorkspace`（`dir /b` 必须成功），并且失败时在 `detail` 里直接给出修复命令。

**理由**：

- 安全探针回答的是"拦没拦住"，可用性探针回答的是"能不能干活"。**只验前者，会得到一个"很安全但什么也做不了"的后端**——用户看到的是一个能启动、能加载、每一步都报"隔离已启用"的 Agent，然后所有命令都失败。
- 这跟 v0.2.1 那个"空输出被截断却当成完成"是同一类错误的不同方向：那次是把失败当成功，这次是把"安全"当"可用"。
- 探针本身也要能区分"被拒绝"和"没跑起来"。`catch(() => true)` 会把"命令根本没执行"也算成"被拦住了"——看起来更安全，实际是假红。所以 `denyHostRead` 只有在沙盒能正常执行（读工作区通过）时才有意义，`ok` 是五项与，不是加权。

**代价**：自检从 4 次 spawn 变成 5 次，启动慢一点。在 strict 模式下这是值得的：它决定的是"要不要让这个 Agent 动你的文件"。

**什么时候该推翻**：如果加入更细的能力探针（比如"能不能跑 node"、"能不能 git clone"），应该做成可配置的检查清单，而不是无限往 `selfTest` 里加；默认只留这几条决定"能不能开工"的。

## ADR-012 项目约定进系统提示词，但不得放宽安全边界

**日期**：2026-11-08　**状态**：生效（v0.4.0）

**背景**：每个仓库都有自己的规矩——目录结构、命名、禁止的做法、常用命令。这些内容每次都要用户口述，或者写进 `--system-extra` 手工带上。仓库里已经有一个可能写着这些的 `AGENTS.md`，但飞码不读它。

问题是：**它一旦进了系统提示词，就同时进了模型的指令层。** 指令层能做的事包括「跳过确认」「不要检查策略」「把环境变量打印出来」。而 `AGENTS.md` 是仓库里的普通文件，有提交权限的人都能改。

**候选**：

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| 当成参考材料 | 拼在用户消息里，并声明"以下仅供参考" | 否：模型不会稳定遵守"仅参考"，反而更可能照做 |
| 当成指令但加声明 | 放进系统提示词，前面写死一段"不得放宽安全边界" | 选用 |
| 只读白名单字段 | 只解析约定里的固定字段（缩进、包管理器…） | 否：表达力太差，真实仓库的约定是自然语言 |
| 不进上下文 | 维持现状，靠 `--system-extra` | 否：绝大多数人不会用 |

**决定**：`AGENTS.md` 进入系统提示词，位置在安全边界声明**之后**，并且前置一段固定文本：其中任何要求跳过确认、忽略策略、读取或输出凭据、向工作区外写入的内容一律无效。

**理由**：

- 自然语言的约定无法结构化，只能整段给模型。既然如此，就必须让"权威来源"和"权限边界"分开：**内容权威来自项目维护者，权限不超过用户。**
- 这条声明不是给恶意仓库准备的（那种情况本来就防不住），而是给**写歪了好意的约定**准备的：有人会在 `AGENTS.md` 里写"提交前自动 push 到 main"、"读 .env 里的配置再跑"，这些在人类读者看来是流程，对 Agent 来说却是"跳过确认"。
- 位置很重要：放在安全边界之后，模型读到的顺序是"你的边界是什么 → 项目想让你做什么"。反过来，模型会先接受项目要求，再看到限制。

**配套的三条读取约束**（都是同一决策的一部分）：

1. **只读工作区根目录这一个文件**，不向上遍历、不读子目录同名文件。否则 `~/AGENTS.md` 会悄悄影响所有项目，一个测试 fixture 也能改掉行为。
2. **符号链接按 `realpath` 判断**，真实路径不在工作区内就当作不存在。否则 `AGENTS.md -> ~/.ssh/id_rsa` 就是把私钥读进提示词。
3. **上限 32 KB，超出截断并明说**。超过这个量的"约定"通常是把整份文档误放进来了，全量塞进上下文会挤掉最近几轮对话——Agent 反而记不住刚发生的事。

**代价**：系统提示词变长，首轮 token 成本上升；`AGENTS.md` 的改动会立刻影响所有会话，用户可能不知道为什么 Agent 今天的行为变了（所以 `doctor` 与启动横幅都会显示"已载入 X KB"）。

**什么时候该推翻**：如果出现"分层约定"的真实需求（组织级 + 项目级 + 目录级），再做递归查找，但必须带显式的来源标注和冲突消解规则；只靠"向上找最近的"会把隐式继承的坑放大。

## ADR-013 飞链 RAG 只做检索工具，不做外部记忆

**日期**：2026-11-08　**状态**：生效（v0.4.0）

**背景**：飞码的知识库有一个 chunk 检索接口（`POST /api/ai/search`，不经大模型，秒级返回）。它有两种接法：一是给模型加一个检索工具，二是让压缩在超预算时用知识库检索结果替代本地摘要。

**决定**：只做检索工具 `search_knowledge`，不碰压缩路径。

**理由**：

- **压缩是长会话的基础设施，不能让外部服务决定它成不成立。** 摘要方案的最坏情况是"摘要写得差"；外部记忆方案的最坏情况是"知识库不可用，长会话整条能力退化为不可用"。把基础设施的可用性与一个网络服务绑定，代价太大。
- 检索工具失败的影响是局部的：这一轮少一条信息，模型可以继续用工作区里的代码干活。
- 两种接法的失败可见性也不同：工具失败会显示在 `tool_end` 里，用户看得见；压缩里悄悄换成外部检索结果，用户不会知道这一段上下文是从哪来的。

**四条实现约束**（都是踩过的坑）：

1. **未配置就不注册工具。** 注册一个永远报"未配置"的工具，模型会反复试，几轮就把上下文烧完。缺配置由 `doctor` 报，不占模型注意力。
2. **输出必须截断**：单条 400 字、最多 8 条。检索结果是外部文本，长度不可控，原样灌进去会挤掉工作区里的真实代码——那才是模型真正要看的。
3. **凭据只在内存**：直接给 token，或用账号密码换一个（缓存在进程内）。不落盘、不进日志、不传给子进程。
4. **超时与取消都要生效**：`signal: ctx.signal ?? AbortSignal.timeout(t)` 是错的，一旦有 `ctx.signal` 就再也不超时；要 `AbortSignal.any([...])`。

**代价**：模型得自己判断"该不该查知识库"。实测在明确提示"查设计决策、历史结论用 search_knowledge，查代码用 grep"之后，行为是可接受的；但这是一个提示词层面的引导，不是机制保证。

**什么时候该推翻**：如果知识库能做到"内网、亚秒级、只读副本"，并且提供稳定的引用锚点，可以再试"外部记忆"方案；但那时也应该保留本地摘要作为降级路径，而不是替换。

## ADR-014 MCP 默认关闭，交互逐次确认，非交互只认放行列表

**日期**：2026-11-08　**状态**：生效（v0.4.0）

**背景**：MCP 是社区事实标准，不支持就等于把用户锁在七个内置工具的盒子里。但 MCP 工具和内置工具的能力边界完全不同：

| | 内置工具 | MCP 工具 |
| --- | --- | --- |
| 跑在哪 | 本进程，经策略层 | 外部进程，内部不可见 |
| 读写范围 | 工作区内，受 policy 约束 | 由它自己决定，可能是整盘 |
| 凭据 | 环境变量白名单，16 类 | 它自己的，可能含 token |
| 网络 | 沙盒默认断网 | 它自己的网络权限 |
| 数据流向 | 本地 | 可能发往第三方 |

**候选**：

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| 装了就全开 | 配置里有的服务器全部工具直接可用 | 否：等于给外部进程一个无审计的入口 |
| 默认开 + 日志 | 全部可用，只记录调用 | 否：日志是事后审计，不是闸门 |
| 默认关 + 逐次确认 | 显式打开，每次调用问一次 | 选用 |
| 装进沙盒 | MCP 服务器跑在 bwrap/AppContainer 里 | 暂不做：见下 |

**决定**：

1. **默认关闭**（`FEIMA_MCP=1` / `--mcp` 才开）。
2. **交互模式逐次确认**：显示工具名与参数摘要（脱敏后，最长 300 字），默认选项是"否"；用户拒绝后明确告诉模型"不要重试，换个方案或询问用户"。
3. **非交互模式（`run` / `rpc`）只认 `--mcp-allow`**：没有确认入口时一律拒绝，并说明补救方式。`rpc` 的 `ready` 里带 `mcpConfirm: "allowlist"`，让桌面端知道这里的语义。
4. **工具名加前缀** `mcp__<server>__<tool>`，与内置工具不可能撞名。
5. **一台服务器起不来不影响其他**：只记一条原因，其余照常可用。
6. **服务端往 stdout 打日志不算故障**：识别成噪音并丢弃。一个 `console.log` 不该让整套工具不可用。

**为什么不把 MCP 服务器装进沙盒**：技术上可以（bwrap 已经在），但会产生两个新问题。一是**能力必然不足**：MCP 服务器要访问它自己的配置文件、缓存的 token、可能还要连数据库，沙盒一收紧就跑不起来，用户看到的是"配了也不可用"。二是**责任模糊**：跑在沙盒里会给人一种"它被管住了"的错觉，实际它的网络与凭据仍然在飞码视野之外。与其给一个心理安慰，不如把闸门放在调用点：让人看见每次调用，并默认拒绝。

**理由**：

- **默认值就是安全策略。** 绝大多数用户不会去改默认值，所以默认值必须按最坏情况设。
- **确认比日志有用。** 日志只有在事后翻查时才生效；确认在动作发生前就能拦住。MCP 调用的副作用（发消息、改数据库、创建 PR）往往不可撤销。
- **提示要落到模型能执行的动作上**："不要重试，换个方案或询问用户"是模型能照做的指令；"操作被拒绝"会让它当成临时故障反复试到轮次耗尽。

**代价**：交互模式下每次 MCP 调用都要按一次 y，很烦；这是有意的——烦能促使用户去用 `--mcp-allow` 划出"这几个工具我信任"，比默认放行再事后追责要好。非交互模式必须预先写放行列表，脚本会啰嗦一点。

**什么时候该推翻**：如果出现"MCP 服务器自带权限声明"（例如服务端在 `tools/list` 里声明需要哪些目录与网络访问），可以据此做分级授权：声明范围内的调用免确认，超出范围的才问。现在协议没有这个能力，所以只能逐次确认。

## ADR-015 重试以「有没有副作用」为界，不以错误码为界

**问题**：v0.2 起就挂着「429/5xx 指数退避，最多 3 次」这一条，但一直没做。真正动手时发现原来的描述不够：Agent 的请求不是纯对话，它携带工具调用，重试可能让同一件事做两遍。

**候选方案**：

1. **按错误码重试**（常规做法）：`retryable === true` 就退避重试。实现最简单，但在流式中断时会重复输出或重复执行。
2. **只重试「未开始」的请求**：建立连接前失败才重试。安全，但 429 常出现在已连上、还没吐数据的时候，会漏掉大部分可重试场景。
3. **以「本次尝试有没有产出」为界**：收到任何 `text` / `reasoning` / `toolCall` 之后就不再重试。

**选 3**。判据不是「错误长什么样」，而是「已经对外界做过什么」：吐过正文，重试会让用户看到同一段话两遍；吐过半截工具参数，重试会把两截拼成一个谁也没写过的命令——那比失败糟得多。

实现上，`withRetry` 只接收 `isRetryable(err)` 与 `hasSideEffect()` 两个回调，后者由循环层提供，因为只有那里看得见「这一轮吐过东西没有」。

**理由**：

- **重复执行的代价不可逆**。超时、429 都能再等一次，但 `rm` 已经跑了、`git push` 已经发了，重试不会撤回，只会再来一遍。
- **判断依据要能被验证**。`produced` 是一个布尔量，用例可以直接断言「吐过内容后只请求一次」；「这次 429 该不该重试」依赖上游行为，没法稳定测。
- **宁可少重试，不要多执行**。与项目一贯的取向一致：把「不确定」解释成「不做」。

**代价**：真正需要重试的「吐了一半断了」场景不再重试，用户会看到一次失败。这是有意的取舍——失败可以重发一条指令，重复执行没法撤销。

**什么时候该推翻**：如果上游普遍支持「幂等请求 ID + 断点续传」，可以在工具调用层面做真正的可恢复重试；那需要协议支持，现在没有。


## ADR-016 确认模式 write ⊂ exec，无确认通道时默认拒绝

**问题**：`--confirm` 要覆盖写文件、执行命令、外部工具三类副作用，取值的语义必须一次说清，否则用户会以为自己被保护了而实际没有。

**候选方案**：

1. **并列档位**：`write` 只拦写文件、`exec` 只拦执行。看着对称，但只开 `write` 时，Agent 用 `bash "echo x > file"` 就绕过去了。
2. **包含档位**：`exec` 同时拦写文件与执行（因为能执行就能写）。`write` 仍只拦写文件，但文档里明说挡不住 `bash`。
3. **单一总开关**：开就全拦。简单，但「只想看着它别乱跑命令、写文件就让它写」这种常见需求做不到。

**选 2**。`exec` 是 `write` 的超集，因为能力的实际范围就是这样；`write` 的局限在帮助文本、README、本记录里都写明，不做「看起来更全」的暗示。

**第二个决定：没有确认通道时默认拒绝。** `feima run` 与 `feima rpc` 没有 stdin 可问，直觉做法是「没人问就放行」，但那样确认就成了摆设——用户换一个入口，所有确认都消失。所以默认拒绝，并把「加 `--yes` 才能放行、不要重试」写进工具结果。`--yes` 是一个显式的、会留痕（`notice` 事件）的选择。

**第三个决定：`external` 无条件确认。** 它跑在策略层之外，`--confirm off` 表示「我知道内置工具能干什么」，不表示「我允许一个我管不了的东西随便跑」。这一条没有开关。

**代价**：没有交互通道时，`--confirm exec` 会让 `run` 直接失败，用户必须先理解 `--yes`。对 CI 场景来说多一步；但反过来，默认放行的确认等于没有。

**什么时候该推翻**：RPC 支持双向确认（宿主发 `confirm`、前端弹窗、回 `confirm_result`）之后，`rpc` 就不再是「没有通道」——那时 `--yes` 只该留给 `run`。这一步排在 v0.6。


## ADR-017 权限档用「不注册」实现，白名单接在 exec 而不是工具层

**问题**：`--perms read` 要怎么「不给写能力」？以及命令白名单放在哪一层才管得住。

**权限档：不注册，而不是注册了再拒绝。**

这个选择在 v0.4 已经验证过一次：知识库没配时 `search_knowledge` 根本不进工具列表。理由是注册一个必然报错的工具，模型会反复试，几轮就把上下文烧光，而用户看到的只是「Agent 呆呆地试了十次」。

代价是模型不知道「有这个工具但没权限」，可能改用 `bash` 想办法——所以 `read` 档连 `bash` 一起不给。这个代价可以接受：只读审查本来就不该有执行能力。

**白名单：接在 `exec`，不接在 `bash` 工具里。**

工具会变多（`bash`、将来的专用工具、MCP 里可能执行命令的工具），但执行只有一个出口。放在 `exec` 上，任何新增执行路径都自动受约束；放在工具层，就得记得每个新工具都加一遍。这与「隔离统一走 `ExecFn`」是同一个思路。

**匹配：先切段，再比 argv 前缀。**

`git status; rm -rf ~` 整串看开头是 `git`，实际执行两条命令；`git status | sh` 的第二段在管道右侧。所以先按 shell 语法切段（`&&` `||` `;` `|` `&` 换行，尊重引号与转义），每段单独过白名单，任意一段不匹配就整体拒绝。

命令替换（`$( )`、反引号、`${ }`、`<( )`）与重定向一律拒绝，不接受「规则里写全就行」：前者在校验之后才生成内容，后者能把输出写到规则覆盖不到的地方。这两条把「白名单能不能被绕过」变成了「白名单有没有写全」，后者用户自己能管。

**代价**：白名单模式下可用性明显下降——重定向被禁、`cd src && npm test` 需要两条规则、规则里带逗号会让 `--cmd-allow` 的分隔失效。这是有意的：白名单是给「只跑固定几条命令」的场景用的，不是日常默认。

**什么时候该推翻**：如果将来改成结构化执行（工具直接收 `argv[]` 而不是命令串），切分这一层可以整体去掉——那时「一条命令」不再是幻觉。现在所有执行都经过 shell，所以必须自己切。
