# 决策记录（ADR）

记录的是**做过判断的地方**，不是功能清单。每条包含：当时的问题、候选方案、为什么选它、付出的代价。

规则：一条决策一旦写入，不删不改结论，后续推翻就追加一条新记录并在旧条目上标「被 ADR-00X 取代」。这样复盘时能看到弯路，而不是只看到一个看似合理的结果。

## ADR-001 自研引擎，不复用 pi-coding-agent

**日期**：2026-11-08　**状态**：生效

**背景**：参考实现 `inkwellio/my-coding-agent` 用的是 `@earendil-works/pi-coding-agent`，引擎能力完整，直接复用能省两周。

**候选**：

1. 复用 pi-coding-agent，只做壳与适配；
2. 自研循环与工具协议。

**决定**：自研。约 320 行的 `core/loop.ts` 承担全部循环逻辑。

**理由**：

- 三个必须改的点都在引擎内部：状态权威（`isStreaming` 的时序）、插话与追加的双队列语义、压缩触发点。用别人的引擎改这三处，等于 fork，后续上游一升级就要重新对齐。
- 要接飞链 RAG 做检索增强，需要在「工具调用前」插入自己的检索决策，外部引擎没有这个钩子。
- 引擎是这类产品的核心资产，不是可替换的依赖。

**代价**：SSE 解析、工具调用片段拼装、增量 JSON 容错都得自己写，这部分在 `providers/openai.ts` 里约 190 行；上游模型的协议差异也要自己适配。

**什么时候该推翻**：如果要支持 Anthropic 原生协议、多模态、prompt caching 这类引擎级能力，自研成本会超过收益，届时应改为 fork + 定期同步上游。

## ADR-002 零运行时依赖，Node 类型擦除直跑 TS

**日期**：2026-11-08　**状态**：生效

**背景**：目标是给团队内和自己长期用，装机摩擦要尽可能低。

**候选**：

1. 常规 TS 工程：`tsc` 构建 + `node_modules`；
2. `esbuild` 打包成单文件；
3. Node ≥ 22.6 的类型擦除，源码直接运行。

**决定**：方案 3。

**理由**：`dependencies` 为空意味着没有供应链风险、没有 `npm audit`、没有版本地狱，改一行代码立刻生效，调试时看到的行号就是源码行号。

**代价（很具体）**：

- 不能用 `enum`、`namespace`、装饰器、构造函数参数属性；
- 类型导入必须写 `import type`（`verbatimModuleSyntax` 要求），否则运行时找不到导出；
- 类型错误不会被拦住——`node` 只擦除不检查，`npm run typecheck` 需要另装 typescript，默认不跑。所以**测试必须比类型检查更密**，这是 38 个用例存在的直接原因。

## ADR-003 CLI 先行，GUI 只做 RPC 客户端

**日期**：2026-11-08　**状态**：生效

**背景**：参考实现是 Electron 桌面端，视觉上更像成品。

**候选**：Electron 先行 / CLI 先行 / 同时做。

**决定**：CLI 先行，桌面端在 v1.0，且**只允许**通过 `feima rpc` 驱动引擎。

**理由**：引擎没稳定时做 GUI，等于把并发、状态、错误处理的问题藏进渲染层——那里最难测、最容易掩盖。RPC 边界强制把「引擎」和「界面」分开，引擎的每个能力都能在没有 UI 的情况下被验证。

**代价**：早期没有可展示的界面；RPC 协议要先定下来，后期改协议的成本高于改内部函数。

## ADR-004 v0.1 只做策略层隔离，strict 失败即阻断

**日期**：2026-11-08　**状态**：生效

**背景**：`@anthropic-ai/sandbox-runtime` 在 Windows 上是 alpha，锁定版本仍有不确定性。

**候选**：

1. 直接引入 srt，赌它可用；
2. 只做策略层（路径、环境、命令过滤），预留后端接口；
3. 不做隔离，先跑起来。

**决定**：方案 2。`--sandbox strict` 在检测不到隔离后端时**直接拒绝执行命令**，不静默降级。

**理由**：安全承诺最怕「看起来开了」。策略层能关掉两条最常被利用的通道（路径穿越、环境变量泄漏），成本低且确定性高；真实隔离留接口，等 Windows Job Object 或 Linux namespace 后端就位再开。

**代价**：`policy` 模式下的命令仍有真实系统权限，只能靠命令过滤兜底。这一点在 `doctor` 和启动横幅里明示，不靠用户猜。

## ADR-005 `isStreaming` 作为唯一状态权威

**日期**：2026-11-08　**状态**：生效

**背景**：源码实证里提到，参考实现在 `agent_end` 之后仍可能发生重试和上下文压缩，界面若见到结束事件就熄灯，会出现「答完了又跳起来」。

**决定**：所有结束判断只读 `snapshot.isStreaming`；`agent_settled` 事件必须在状态已落回 `idle` 之后才发出。

**实现约束**：`submit()` 里先 `busy=false; state="idle"` 再 `emit("agent_settled")`，顺序不能反；有专门用例断言「settled 时 isStreaming === false」。

**代价**：事件不再自解释，UI 收到任何事件都要回头查一次快照。多一次调用，换来状态不可能错。

## ADR-006 上下文压缩用摘要，切分点只落在 user

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：v0.1 没有压缩，长会话会顶到模型上限；一旦超限，上游报错或悄悄丢历史，表现是「刚看过的文件又问一遍」。

**候选**：

1. 滑动窗口，直接丢最早的 N 条；
2. 把早期消息交给模型摘要，替换成一条摘要消息；
3. 检索式记忆（把历史当向量库，按需召回）。

**决定**：方案 2；方案 1 作为摘要不可用时的降级；方案 3 留到接入飞链 RAG 时再做。

**理由**：

- 直接丢会丢掉「用户最初的目标」和「改了哪些文件」，这两类信息一旦丢了，后续所有操作都可能在错误前提上继续。
- 摘要能保留结论与路径，成本是一次额外模型调用。
- 检索式记忆最省 token，但要向量库和嵌入模型，会把零依赖这条打破，等 RAG 接入时一并做。

**三条硬约束（写进代码注释与测试）**：

1. **系统提示永不折叠**。它定义行为边界，摘要成一句话就丢掉了约束力。
2. **切分点只能落在 `user` 消息上**。`assistant(tool_calls)` 和紧随的 `tool` 结果是一对，切在中间上游会直接报 400（找不到对应的 `tool_call_id`）。
3. **压缩必须真的变小**，否则放弃本次压缩。否则出现「越压越长」的荒谬情况。

**降级链**：模型摘要 →（失败）规则摘要 →（还不够小）不压缩。规则摘要只列用户诉求、调用过的工具、最后几条结论，绝不编造。

**代价**：压缩本身要一次模型调用，短会话压缩不划算，所以设了「可折叠内容不足 3 条就不压」的门槛；摘要必然有损，重要细节靠模型重新读取文件来找回。

## ADR-007 会话用 JSONL append-only，存 `~/.feima`

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：v0.1 退出即丢历史，长任务中断后只能重来。

**候选**：

1. 单个 JSON 文件，每次全量写入；
2. SQLite；
3. JSONL append-only，一行一条记录。

**决定**：方案 3，目录 `~/.feima/sessions/`，文件名 `<时间戳>-<随机4位>.jsonl`。

**理由**：

- **崩溃安全**：进程被 kill 时最多丢最后半行，前面的历史完整可读；全量写 JSON 则整个文件可能变成半截，一条都读不回来。
- **可观测**：`tail -f` 就能看 Agent 在做什么，不需要查看器。
- **可演进**：新增记录类型（压缩、用量、备注）只是多一种行，旧版本读到不认识的类型跳过即可。
- **不写工作区**：会话里有敏感路径和业务信息，放仓库里容易被误提交；跨项目检索时按 `meta.workspace` 过滤。

**实现细节（都是踩过的坑）**：

- append 前检查文件末尾是否以 `\n` 结束，不是就先补一个。否则新记录会粘到残行后面，把两条都变成坏行。
- 读取时坏行跳过并计数，恢复横幅会提示「跳过 N 行损坏记录」。
- 首条用户消息自动成为标题，并**重写第一行 meta**。只改内存会导致列表里永远显示「未命名会话」。
- 恢复时系统提示用**当前配置重新生成**，不沿用会话里那条——工作区变了、提示词改了，旧约束带回来是负担。

**代价**：没有索引，`list` 要扫目录读每人的首行；会话多了会慢（几百个以内无感）。真要做检索再上 SQLite，接口已经收敛在 `SessionStore` 里。

## ADR-008 压缩预算用字符估算，不引入 tokenizer

**日期**：2026-11-08　**状态**：生效（v0.2.0）

**背景**：判断「该不该压缩」需要一个 token 数。

**候选**：

1. 引入 `tiktoken` / 模型自带 tokenizer，精确计数；
2. 按字符估算：中日韩 1.05 token/字，其他 3.6 字符/token。

**决定**：方案 2。

**理由**：tokenizer 是几十 MB 的原生依赖，且不同厂商分词器不同，为了一个「是否压缩」的阈值引入它不划算。估算误差在 15% 以内，只要阈值留足余量（32k 上下文按 22000 触发）就不会误判。

**代价**：真实计费以 `usage` 为准，估算值不能用来算钱；`/context` 显示的是近似值，标注为「约」。

**什么时候该推翻**：如果要做「精确预算分配」（比如按剩余额度决定压缩多少轮），估算精度不够，届时按 provider 引入对应 tokenizer。

## ADR-009 压缩切分点：轮次优先，token 兜底

**日期**：2026-11-08　**状态**：生效（v0.2.1）

**背景**：v0.2.0 的切分点只按「从尾部数第 N 个 user 消息」算。做长任务验收时发现一个致命空档：**一轮任务里跑了 25 次工具调用，整条历史只有一条 user 消息，`findCut` 返回 -1，压缩一次都不会触发。** 上下文从 3k 一路涨到上游上限，模型开始反复读同一个文件——不报错，只是变笨。这条在 v0.2.0 的遗留清单里写着「单轮内超长工具链不中途压」，实际比预想的严重：不是「压得不够勤」，是「完全不压」。

**候选**：

1. 固定保留最近 K 条消息，按条数切；
2. 只按 token 切：从尾部累积到 `keepTokens` 为止；
3. 双策略：有足够用户轮次时按轮次切，否则按 token 切。

**决定**：方案 3。

**理由**：

- 方案 1 在「一条消息 5 万字符」时完全失效——留 10 条也可能是 8 万 token。
- 方案 2 会切掉用户最近的诉求。多轮对话里，用户三句话之前说的约束，比三倍体积的工具输出更重要；纯 token 切法不看语义边界，容易把「把版本改成 0.2.0」这种关键指令折进摘要。
- 方案 3 保留了两种场景各自的最优解：多轮对话看轮次，单轮长链看 token。

**实现约束**（比策略本身更容易出错）：

- 切点不能落在 `tool` 消息上，否则 `assistant(tool_calls)` 被折走、结果还在，上游直接 400。落到 tool 上就右移到整组结束，宁可多留。
- 摘要消息是 `role: "user"`，必须排除在轮次计数之外。否则第二次压缩会把切点算到摘要前面，折叠区只剩一条摘要，触发「可折叠内容不足」，压缩永久停滞。
- 压缩后必须真的更小，否则回退——`keepTokens` 设得过大时会命中这条保护。

**代价**：多一个配置项（`keepTokens` / `FEIMA_KEEP_TOKENS`），多一个分支。两种策略的交互需要专门的用例守：长工具链测试（配对完整性）、连续三次压缩（摘要不累积）。

**什么时候该推翻**：如果接入按「任务」划分的结构化历史（把一轮任务显式切成阶段），切分点应该由阶段边界决定，而不是靠轮次或 token 猜。
